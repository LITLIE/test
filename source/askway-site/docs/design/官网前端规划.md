# 问途 AskWay 官网前端规划

日期：2026-11-24，Asia/Hong_Kong。状态：可审阅的规划草案。官网首要目标“突出品牌形象与合作价值”已经由用户确认；本文的视觉方向、页面范围与实现架构是推荐方案。本轮交付技能安装和规划文件，前端实现属于后续阶段。

## 1. 官网定位与成功目标

把问途呈现为“商讨式行程规划与城市游览助手”：将出游条件、可行行程、地图调整和手机现场执行衔接起来，从珠海城市游览场景出发，探索更连贯的城市体验。

优先服务景区与文旅机构、城市内容团队、酒店与目的地服务方，以及希望了解问途产品的访客。首页需要依次回答：问途是什么、已经具备什么能力、能够一起探索哪些场景、如何进一步沟通。

建议的品牌主张：**让每一次城市探索，都有清晰的方向。**

建议的首屏说明：**问途连接出游偏好、可行行程与现场游览，从一段城市旅程出发，探索更连贯的城市体验。**

主行动按钮为“探讨合作”，进入合作页面；次行动按钮为“了解问途”，进入产品页面。产品演示入口作为了解能力后的进一步行动，根据实际可访问的演示地址配置。

完成标准围绕四个结果：品牌识别鲜明；访客能够理解产品闭环；合作方向具体且有清晰的沟通路径；手机与桌面访问均顺畅。访问量、点击率与合作转化率在正式上线后记录，规划中的目标不作为已有业绩展示。

## 2. 已核实的项目基础

| 项目事实 | 对官网的影响 |
|---|---|
| 当前项目是问途 AskWay，具备 React Web、Kotlin Android 与 Node 服务端 | 品牌内容应以真实产品闭环为核心 |
| Web 使用 React 18、Vite 5、TypeScript、React Router 6、MUI 5、Tailwind 3 | 官网延续 React、Vite 和 TypeScript 的技术路线，团队学习成本可控 |
| 当前根路由跳转 /plan，另有 /trips | 官网与产品入口的地址需要明确映射 |
| main.tsx 全局挂载 AppProvider、MUI ThemeProvider 与 CssBaseline；AppProvider 初始化会请求健康状态、景点和业务条件 | 官网采用独立入口、布局和构建，浏览品牌内容无需启动业务状态 |
| 现有品牌色为蓝色 #0B6E99 与琥珀色 #E8A33D | 视觉体系延续品牌辨识，增加深海色和温暖留白 |
| 珠海情侣路与野狸岛是已有产品场景基础 | 首页城市意象和示例围绕已有场景展开 |
| 当前材料同时包含历史版本、G1–G5 交付和后续 G6 规划 | 官网内容按当前源码与最新明确记录核实；历史评估中的缺口不能直接当成今天的状态 |

本次只核实适合官网规划的源码和文档事实，没有重新执行产品业务回归，也没有验证公众访问地址、应用市场上架或合作合同。

## 3. 三种视觉方向及选择

| 方向 | 表达方式 | 优势 | 取舍 |
|---|---|---|---|
| A · 海岸城市 × 可信科技（推荐） | 海岸摄影或城市意境、大标题、精确网格、真实产品画面、少量路线线条 | 问途的城市特色与合作方需要的专业感兼顾 | 需要精心选择影像，并对产品截图进行整理 |
| B · 极简商务 × 解决方案 | 高对比排版、能力结构、合作路径和方案说明 | 信息效率高，适合合作洽谈 | 品牌情绪和城市记忆点较弱 |
| C · 沉浸影像 × 城市文化 | 大幅实景、城市故事、文化内容和渐进叙事 | 感染力和文旅属性强 | 素材要求与加载成本较高，产品价值需要额外强调 |

本草案先按 A 展开。采用精确的编辑式排版组织信息，把城市情绪放在重点画面，把产品能力放在可核实的界面与流程中。

## 4. 首版页面范围与导航

首版建设四个正式页面。桌面导航为“产品体验、合作方向、关于问途”，右侧设置“探讨合作”。移动端保留字标与菜单按钮，菜单内按相同顺序呈现入口。

| 路由 | 任务 | 主要内容 | 核心行动 |
|---|---|---|---|
| / | 建立品牌印象，串联产品与合作价值 | 首屏、品牌理念、产品闭环、珠海示例、合作方向、信任依据 | 探讨合作、了解问途 |
| /product/ | 让访客理解真实产品 | 对话与条件确认、可行性校验、地图与方案调整、跨端保存、手机执行与讲解 | 查看演示说明；配置有效地址后进入产品 |
| /cooperation/ | 让合作方找到切入点 | 合作场景、双方投入、可讨论的试点方式、沟通步骤、官方联系渠道 | 邮件联系、复制邮箱 |
| /about/ | 解释品牌理念与项目基础 | 产品出发点、阶段进展、公开可核实的信息、团队介绍 | 返回产品或合作方向 |

合作页末尾承担联系功能，首版使用正式邮箱和复制邮箱入口。它无需新增线索数据库；邮件应用无法打开时，访客仍可复制地址。团队名称、联系方式和成员资料均由负责人确认后上线。若未来需要站内表单，再设计真实接收、失败反馈与数据处理流程。

下载、新闻中心、多语言与更多解决方案作为后续扩展，根据真实运营需要安排。首版集中完成上述四页的内容、体验和质量。

## 5. 首页叙事与布局

| 顺序 | 区块 | 具体内容与作用 | 视觉和交互 |
|---|---|---|---|
| 1 | 品牌首屏 | 品牌主张、简短说明、主次行动按钮 | 左侧清晰文字，右侧或背景为海岸主视觉；叠加少量路线线条和经过整理的产品画面 |
| 2 | 从想去到可行 | 提出“表达偏好—确认条件—形成安排—现场游览”的品牌逻辑 | 宽留白、短句与编号，建立阅读节奏 |
| 3 | 产品闭环 | 展示“商讨、规划、调整、执行”四个阶段 | 手动切换阶段与对应截图；每次切换都提供文字说明，移动端可纵向阅读 |
| 4 | 珠海示例 | 以已有城市场景说明路线如何衔接景点和游览过程 | 自制路线示意与实景组合；标明“场景示例”，具体时间与价格经过核实后使用 |
| 5 | 值得信赖的细节 | 条件确认、独立校验、变化解释、版本确认，以及信息未知时的明确提示 | 三到四组简洁的界面细节与解释，建立产品可信度 |
| 6 | 一起探索的方向 | 内容共建、城市体验试点、目的地服务衔接 | 三类合作方向，分别说明适合谁、可讨论什么、下一步是什么 |
| 7 | 项目基础 | 用公开可核实的产品进展、界面或阶段说明回答“现在做到哪里” | 文字与简明时间线；每项有真实依据和日期 |
| 8 | 合作邀请 | 简短邀请、合作入口与产品了解入口 | 深海色背景，明确的“探讨合作”行动按钮 |
| 9 | 页脚 | 字标、页面导航、正式联系渠道与适用政策链接 | 简洁、可阅读、可操作 |

页面按正常文档顺序阅读。章节出现可以有轻量动画，但正文在关闭动画或 JavaScript 尚未运行时仍能阅读。核心信息由文字与画面共同表达。

## 6. 合作价值的写法

合作场景是可讨论的方向，并非已有合作或已交付解决方案。

| 潜在对象 | 可讨论的切入点 | 页面上提供的具体信息 |
|---|---|---|
| 景区、文旅机构与城市内容团队 | 自有景点内容共建、讲解内容完善、单片区游览体验试点 | 已有产品流程、内容样例、试点范围、内容核实与授权要求 |
| 酒店与目的地服务方 | 从酒店出发的城市游览场景、行程与本地内容的衔接 | 用户场景、现有能力、需要进一步核实或开发的部分 |
| 校园与研究协作团队 | 产品体验研究、可解释规划、跨端体验验证 | 已有项目基础、可讨论的研究问题、合作沟通路径 |

建议合作流程为：明确场景与目标 → 共同确定有限试点 → 内容与方案核实 → 体验验证与复盘。业务效果、价格、API 接入、白标能力和上线时间依据实际协议与实现另行确定。

官网展示的客户、合作方标识、用户评价、覆盖城市和量化业绩必须有对应证据。暂未获得这类材料时，以真实产品能力和场景示例承担信任建设。

## 7. 视觉设计系统草案

### 色彩

| 语义 | 色值 | 用法 |
|---|---|---|
| brand.primary | #0B6E99 | 品牌强调、主要按钮、链接 |
| brand.deep | #082D3D | 深色章节背景、重点标题 |
| brand.accent | #E8A33D | 小面积路线节点、重点标记、深色文字的强调按钮 |
| surface.page | #FAF9F6 | 温暖的主背景 |
| surface.card | #FFFFFF | 产品画面和少量功能容器 |
| text.primary | #173441 | 正文与标题 |
| text.secondary | #52646D | 辅助说明 |

对白色按钮文字配品牌蓝的静态对比度为 5.67:1；深色正文配主背景为 12.44:1；辅助文字配主背景为 5.86:1。琥珀色背景搭配深海色文字为 6.70:1，配白字只有 2.16:1，因此琥珀色按钮使用深色字。照片背景上文字的实际对比度在成稿时逐处检查。

### 排版与空间

中文主体使用系统中文无衬线字体，保持与已有品牌的一致性；需要稳定字形时，可将授权明确的 Noto Sans SC 子集作为本地静态资源。首次访问的可读性不依赖外部字体服务。

桌面主标题建议 64–80px，移动端 36–44px；正文 16–18px，中文行高 1.65–1.8。标题按语义分行，避免依赖极窄固定宽度形成残缺末行。正文限制阅读宽度；英文字标与中文标题保持独立的层级关系。

内容最大宽度约 1200–1280px，桌面采用 12 列网格；手机侧边留白 20–24px。区块纵向间距随屏幕从 64px 到 120px 调整。按钮和菜单主要触控区域至少 44×44 CSS px。

容器以简洁边界、留白与图文关系形成层次。产品演示容器可用 12–20px 圆角，其他区块由编辑式排版承担结构。图标使用单一 SVG 图标体系，自有品牌符号单独维护。

### 动效

按钮与菜单反馈约 120–200ms，章节进入约 400–600ms，位移控制在 12–24px。路线示意允许一次性的轻量路径出现效果；切换产品阶段由用户操作。仅在视区中运行必要动画，优先使用 opacity 和 transform。

开启 prefers-reduced-motion 时直接呈现最终可阅读状态。导航、图片说明、路线阶段和行动按钮的可用性独立于动画。

## 8. 技术架构与产品衔接

推荐在现有问途仓库的 dev/askway-site/ 建设独立官网前端，采用 React 18、Vite 5、TypeScript 与 Tailwind 3。官网组件与样式保持轻量，品牌色和字标按统一约定维护。规划端继续承担实际行程操作。

独立入口避免官网首页挂载业务 AppProvider、地图 SDK、登录对话框与工作台状态。官网的产品流程展示使用经过整理的截图和自有示意数据；真实产品入口按有效地址配置。

| 层级 | 职责 |
|---|---|
| SiteLayout | 官网导航、页脚、菜单、跳转与全站阅读结构 |
| 页面 | 首页、产品页、合作页、关于页的内容编排 |
| 品牌组件 | 字标、主视觉、产品阶段展示、场景示意、行动按钮 |
| 内容与配置 | 已核实的能力描述、公开联系信息、素材来源、产品访问地址 |
| 静态构建 | 为四个路径输出可直接阅读的 HTML、页面元信息与静态资源 |

品牌官网采用静态预渲染。每页输出独立 title、description、canonical、Open Graph 元信息，并生成 sitemap 与 robots；canonical 在正式域名确认后配置。直接访问和刷新每个页面路径都应成功。

网站主域名与产品地址分开配置。部署时可将官网放在主域名，将现有产品放在 app 子域名或明确的产品路径；具体映射由实际托管环境决定。旧产品链接的连续性在接入阶段验收。

官网安装和构建只使用工作区内的依赖、临时目录及缓存；依赖列表按官网需要选择。生产依赖由工具选择适配平台，避免照搬现有 Web 中直接指定的 Windows 二进制包。

| 产品说明 | 条件确认、校验、调整、保存与执行对应真实能力 | 产品页与信任区块 |

正式域名、官方联系渠道、可公开的团队资料、主视觉授权以及有效产品演示地址，是上线前需要落实的内容输入；它们不阻碍当前设计与本地前端制作。

## 11. 验收标准

检查 360、390、768、1024、1440、1920px 代表宽度及手机横屏。页面无水平溢出；导航、正文、截图和合作入口在 200% 浏览器缩放下可用；触控与键盘路径均能完成主要操作。

检查标题结构、跳到正文入口、菜单焦点与 Escape 关闭、照片替代文本、截图说明、可见焦点以及 sticky 导航对锚点和焦点的遮挡。普通文本对比度至少 4.5:1，主要控件和有意义图形至少 3:1。关闭动效后完整内容和操作保持可用。

首页主视觉提供适当尺寸的 WebP/AVIF，预留图片比例；首屏关键图及时加载，后续图片按需加载。以固定浏览器、移动设备模拟和网络限制记录实验室性能：Lighthouse Performance 目标至少 90；实验室 LCP 目标不超过 2.5s、CLS 不超过 0.1。正式上线后另用真实用户数据检查 INP 不超过 200ms，实验室检查不作为真实用户指标已达标的证明。

四页静态 HTML 包含真实正文和元信息；所有导航、产品入口与联系渠道可达；合作场景与业绩表述有依据；没有未实现的交互被显示为成功。验收报告保留实际浏览器、屏幕宽度、条件、结果与剩余事项。
